# 创建参数修复真实模型对照

复跑此前发生两次 JSON 解析错误的端口校验案例：使用内置功能开发模板 v1 的五节点结构，为 `validatePort(value)` 生成需求、人工需求确认、实现、独立验证和人工最终验收任务。仅测试创建适配，不启动执行成员。

宿主固定 Harness 0.2.1-rc.2，模型为现有 DeepSeek 账号的 deepseek-flash / high。每版使用独立 Profile、工作区和新会话，workspace-write 权限，最多 12 次模型请求。运行顺序为 dev.7、dev.6；两轮串行。dev.6 来自修复前提交的归档产物，dev.7 来自已经验证的打包产物。

| 本次实测 | 0.2.5-dev.6 | 0.2.5-dev.7 |
| --- | --- | --- |
| 模型请求 | 10 | 5 |
| 提案提交 | 7 | 3 |
| 被拒绝提案 | 6 | 2 |
| 适配耗时 | 275.787 秒 | 89.526 秒 |
| 最终结果 | 成功 | 成功 |

耗时从打开适配讨论的 HTTP 响应到测试驱动确认应用的响应，不含宿主启动。两轮最后仍为 staged，五个任务全部 pending，成员均未创建执行会话；模板通用要求与依赖未变。适配通过后即退出，不包含代码实现、任务执行和最终人工验收。

每版仅一个样本，没有固定模型随机性，网络和服务负载也不受控。结果表明这一轮修复版的重试更少，不能据此承诺稳定成功率或固定提速比例，更不能代表用户其他服务器上未指定的小模型。

## 剩余问题

dev.6 六次失败分别涉及：更改不可变通用层、漏传 general、只提交部分节点，以及再次更改通用层。

dev.7 第一次把 confirmConfiguration 放进 layers 内部，被 Schema 拒绝；第二次把“无缺失信息，可直接具体化”等正常说明填进 adaptationIssue，同时要求确认配置，被业务校验拒绝。第三次修正后成功。这两次错误均未修改团队或触发执行。

因此本批修复尚未让适配一次成功。后续应优先让模型只提交节点 ID 和本次任务内容，由服务端保留通用层并维护配置状态；问题说明字段应明确只接收阻塞问题，不能作为普通适配备注。

## 错误参数回放

从原 feature-live-3 轨迹取出两条真实失败参数，仍能复现 JSON.parse 在字符 1823、1554 的错误。直接交给新版则在 operations 数组校验处拒绝，不会自动修复字符串内容。原成功提案转换为原生数组后，通过新版 Schema 和操作解析。

用户报告的 layers 错误没有原始调用参数，因此另行构造字符串化对象、数组、空字符串、null 四种输入。新版均拒绝，并返回 operations[0].layers must be an object。正确对象和六个字符串字段通过。此处不能声称新版会自动接受或纠正错误类型；工具 Schema 仍会先于业务解析器拒绝它们。
