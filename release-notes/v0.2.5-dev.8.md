# 0.2.5-dev.8 — 两阶段任务生成

仅 dev 开发版本；main / classic 不变，未发布到 npm。

- 新建流程先调用 `agent_teams_plan_general` 保存成员、节点、依赖和通用任务草稿，再调用 `agent_teams_plan_specific` 生成完整本次任务。通用草稿持久化，中断后可以恢复；第一阶段不会创建执行成员或任务。
- 第二阶段的模型上下文明确包含当前目标、每个节点的通用要求/交付物/验收要求、负责人和依赖。正常输出仅包含任务 ID 与三个文本字段；不再要求模型重复 general、layers、配置状态或操作联合结构。服务端保留通用层和 DAG，拒绝漏节点、重复 ID 和过期草稿。
- Gallery 模板已有通用层，直接执行第二阶段。真正缺失信息时可报告 blocker；普通说明不再使用容易误填的 adaptationIssue。执行 Agent 仍只接收完整的本次任务，因此第二阶段必须把所有通用约束具体化纳入本次层。
- `/teamflow` 队长入口使用 `create(approval=required, plan.tasks[].general)`，随后 `edit_plan(update_task, specific)`。创建结果与中断后的状态读取均返回保存的通用要求、目标和真实任务 ID，完成前禁止启动。已有 profile、旧参数接口继续兼容。
- 两阶段之间无需用户确认，最终一次预览确认后才可启动。这里的“两次”是两次生成提交；上下文读取、模型最终说明、错误重试可能产生额外工具或模型请求。

验证结果与真实模型试跑见 [实测报告](../docs/two-stage-planning-trial-2026-11-02/README.md)。结构校验不能证明模型语义完整覆盖所有通用约束，最终预览仍需检查。
